
	
<description>
The `modbus_reply` function is responsible for handling a Modbus request and generating an appropriate response. It parses the request packet, which is provided in the `req` buffer, to determine the requested action (e.g., read coils, write registers). The function then interacts with the `modbus_mapping_t` structure, which holds the device's data (coils, registers, etc.), to either retrieve the requested data or update it. Finally, it constructs a response packet and sends it back to the Modbus master. The `modbus_t` context contains the backend-specific information and functions required for communication, such as the header length and functions for building the response. The `req_length` parameter is crucial for validating the integrity of the request packet.
</description>
<requirements>

<requirement>
The `ctx` argument, a pointer to a `modbus_t` structure, must be initialized by calling either `modbus_new_tcp` or `modbus_new_rtu`. This is because the function relies on backend-specific function pointers within the `modbus_t` structure to process the request and build the response.
</requirement>
<requirement>
The `mb_mapping` argument must be a valid pointer to a `modbus_mapping_t` structure, which should be allocated and initialized using the `modbus_mapping_new_start_address` function. This is because the function reads from and writes to the data tables within this structure (e.g., `tab_bits`, `tab_registers`) based on the request.
</requirement>
<requirement>
The `req` buffer must contain a well-formed Modbus request, and `req_length` must be the correct length of that request. The function performs various checks based on the assumption that `req` is a valid request, and an incorrect length or format can lead to buffer over-reads or other memory-related errors.
</requirement>
<requirement>
The function code in the `req` buffer should be one of the supported `MODBUS_FC_*` constants, and the data address should be within the valid range defined in the `mb_mapping` structure. This will ensure that the function can process the request without immediately returning an `ILLEGAL_DATA_ADDRESS` or `ILLEGAL_FUNCTION` exception.
</requirement>
<requirement>
The data tables within the `mb_mapping` structure (e.g., `tab_bits`, `tab_registers`, `tab_input_bits`, `tab_input_registers`) must be initialized with valid data. This is because the function directly accesses these tables to fulfill read and write requests, and uninitialized data could lead to unpredictable behavior or crashes.
</requirement>

</requirements>

#include <arpa/inet.h>
#include <errno.h>
#include <netinet/in.h>
#include <pthread.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

#include <sys/socket.h>
#include <unistd.h>

#include "modbus.h"
#include "/src/libmodbus/fuzz/unit-test.h"

#define PORT 8080
#define kMaxInputLength MODBUS_TCP_MAX_ADU_LENGTH

// Data to be passed to the client thread
typedef struct {
    const uint8_t *data;
    size_t size;
    uint16_t port;
} client_args_t;

// Client thread: connects to the server and sends the fuzzed data
static void *client_thread_func(void *args) {
    client_args_t *c_args = (client_args_t *)args;
    int s;
    struct sockaddr_in server_addr;

    // Give the server a moment to start listening
    usleep(10000);

    s = socket(AF_INET, SOCK_STREAM, 0);
    if (s < 0) {
        return NULL;
    }

    memset(&server_addr, 0, sizeof(server_addr));
    server_addr.sin_family = AF_INET;
    server_addr.sin_port = htons(c_args->port);
    server_addr.sin_addr.s_addr = inet_addr("127.0.0.1");

    if (connect(s, (struct sockaddr *)&server_addr, sizeof(server_addr)) < 0) {
        close(s);
        return NULL;
    }

    // Send the raw fuzzed data as a request
    send(s, c_args->data, c_args->size, 0);

    // Wait for a potential reply to avoid connection reset issues
    char dummy_buf[MODBUS_TCP_MAX_ADU_LENGTH];
    recv(s, dummy_buf, sizeof(dummy_buf), 0);

    close(s);
    return NULL;
}

// Fuzz entry point
int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
    // Input size validation
    if (size < 1 || size > kMaxInputLength) {
        return 0;
    }

    // --- Start client thread to send the fuzzed data ---
    pthread_t client_tid;
    client_args_t c_args = {data, size, PORT};
    if (pthread_create(&client_tid, NULL, client_thread_func, &c_args) != 0) {
        return 0;
    }

    // --- Run server logic in the main thread ---
    modbus_t *ctx = NULL;
    modbus_mapping_t *mb_mapping = NULL;
    int server_socket = -1;
    int master_socket = -1;
    uint8_t query[MODBUS_TCP_MAX_ADU_LENGTH];
    int rc = 0;

    ctx = modbus_new_tcp("127.0.0.1", PORT);
    if (ctx == NULL) {
        goto cleanup;
    }

    // Set a timeout for the server to avoid hanging
    modbus_set_response_timeout(ctx, 0, 200000); // 200ms

    mb_mapping = modbus_mapping_new(UT_BITS_NB, UT_INPUT_BITS_NB,
                                    UT_REGISTERS_NB, UT_INPUT_REGISTERS_NB);
    if (mb_mapping == NULL) {
        goto cleanup;
    }

    server_socket = modbus_tcp_listen(ctx, 1);
    if (server_socket == -1) {
        goto cleanup;
    }

    master_socket = modbus_tcp_accept(ctx, &server_socket);
    if (master_socket == -1) {
        goto cleanup;
    }

    rc = modbus_receive(ctx, query);
    if (rc > 0) {
        // Call the function-under-test with the received fuzzed data
        modbus_reply(ctx, query, rc, mb_mapping);
    }

cleanup:
    // Wait for the client thread to finish
    pthread_join(client_tid, NULL);

    // The modbus_tcp_accept documentation states not to close the returned socket.
    // modbus_close(ctx) handles it.
    if (server_socket != -1) {
        close(server_socket);
    }
    if (mb_mapping != NULL) {
        modbus_mapping_free(mb_mapping);
    }
    if (ctx != NULL) {
        modbus_close(ctx);
        modbus_free(ctx);
    }

    return 0;
}
