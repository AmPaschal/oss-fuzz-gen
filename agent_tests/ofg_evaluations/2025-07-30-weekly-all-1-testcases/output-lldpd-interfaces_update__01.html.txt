
	
<description>
The `interfaces_update` function is responsible for refreshing the daemon's internal representation of the system's network interfaces. It is a Linux-specific implementation that uses netlink sockets to query for a list of interfaces and their IP addresses. For each interface, it gathers additional details such as the hardware driver, wireless properties, and membership in bonds, bridges, or VLANs. This information is then used to create or update `lldpd_hardware` structures within the main `lldpd` configuration object (`cfg`). The function also handles applying allowlists, configuring management addresses, and setting promiscuous mode on interfaces. Its correct execution is critical for the daemon's ability to send and receive LLDP frames on the correct ports with accurate information. The function's behavior is heavily dependent on the capabilities of the local chassis, as indicated by flags in `LOCAL_CHASSIS(cfg)->c_cap_available`.
</description>
<requirements>
<requirement>
The `cfg` argument, a pointer to `struct lldpd`, must be allocated and initialized. This is because the function dereferences this pointer extensively to access and modify global daemon state.
</requirement>
<requirement>
The `g_chassis` list within the `cfg` structure must be initialized and contain at least one entry for the local chassis. The function uses the `LOCAL_CHASSIS` macro to access this entry, and an empty list would result in a NULL pointer dereference.
</requirement>
<requirement>
The `g_hardware` list in `cfg` must be an initialized TAILQ. The function iterates over this list to perform updates, so it must be a valid queue.
</requirement>
<requirement>
Before calling `interfaces_update`, `netlink_init(cfg)` must be invoked to initialize the netlink subsystem. This is because the function's first action is to call `netlink_get_interfaces` and `netlink_get_addresses`, which will fail or crash if `cfg->g_netlink` is not set up.
</requirement>
<requirement>
The `c_cap_available` member of the local chassis should be fuzzed with various combinations of `LLDP_CAP_*` flags (e.g., `LLDP_CAP_WLAN`, `LLDP_CAP_BRIDGE`). This is because these flags control conditional code paths for discovering different types of interfaces.
</requirement>

</requirements>
